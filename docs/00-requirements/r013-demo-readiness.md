## 1. 范围（本轮做）

### A 三人档焦点 bug（修，优先级最高）
现象（r009.5 登记、`docs/00-project/global-roadmap.md` §9）：三人档下房主在举手格点「给焦点」后，**被给焦点那端正确**，但**房主自己的界面**没进焦点布局（`data-stage-mode=uniform`、`.is-focus`=0）；两人档两次运行两端同步。
本轮要求：三人档「给焦点」后，**三端都应一致进入 focus 布局**（同一 `focusIdentity`、`.is-focus` 恰好 1 格、房主端也放大）。
侦察结论（本轮读码，design §2 展开）：焦点布局要三个条件同时成立——(a) `focusUserId` 非空、(b) 该人在 `members` 里 `status==='active'`、(c) 该人在 `identities`（有轨道的参与者）里。三处都是候选落点，**以真机复现定案，不猜着改**。

### B 服务端强停共享（取证 + 必要时修）
现状：`useScreenShare` 已订阅 `TrackUnpublished` / `ParticipantDisconnected` → 重算共享者，理论上别人关标签就应自动清格；但 **r004 未闭合④ 至今无实测**（`docs/rounds/r011-debt-backfill/manual-verification.md` MV-2 是人工项）。
本轮要求：真机造「共享者不点停止、直接关标签/断连」→ 记录另一端**清格耗时**（秒）与是否停在最后一帧；若 > 10 秒或不清，按取证结果修（候选见 design §3）。数字回填 r004 review 未闭合④ 与 r011 人工剧本 MV-2。

### C 转写 worker 自愈与可观测（不升级依赖）
现状：worker 曾因 LiveKit FFI panic 退出（`timed out waiting for ReadyForRoomEventRequest`），靠 `agents.bat` 自动重启兜；心跳已上报（r011 cp-5）。
本轮要求：(1) `entrypoint` 的 `ctx.connect()` 加**有限重试 + 退避**，失败时写结构化日志并**以非零码退出**（交给守护脚本重启），不再裸崩；(2) 心跳上报带 `lastError`，后端内存态保存并由 `/api/rooms/{id}/stt-status` 透出，前端芯片能显示「worker 起不来：<原因>」。
**不做**：升级 `livekit-agents`（需你批，见 §2）。

### D 房间结束后的只读回看页 `/rooms/:id/replay`
现状：房间结束后列表里只有「已结束」徽标，**没有任何入口**（原入口随 redirect-06 删管理页一起消失，`docs/00-project/global-roadmap.md` §9 登记为能力缺口）。
本轮要求：新只读页，三段内容——**时间线**（聊天 + 系统消息 + 转写，正序，复用 `GET /api/rooms/{id}/conversation`）、**纪要**（复用 `GET /api/rooms/{id}/summary`）、**成员**（显示名 / 角色 / 加入与离开时间）；入口 = 房间列表页 `ended` 房卡的「回看」按钮。
权限口径（默认，§10 Q1 待你确认）：房主 / 历史协管 / 超管，以及**当时在册的成员**可看；其他人 403 并给「仅当时在册成员与管理身份可回看」。

### E 全服大屏并入交流页抽屉（口径变更）
现状：大屏是独立右侧面板（r012 Q11=2），且我按「避免双抽屉」在交流页**不渲染**入口（r012 cp-8）。你现在要它进交流页。
本轮要求：把大屏面板内容拆成可复用组件，交流页右抽屉加**第四个 tab「大屏」**（讨论 / 成员 / 邀请 / 大屏）；常规页仍用顶栏「大屏」开合独立面板；交流页顶栏按钮继续不渲染（入口在抽屉里）。
**口径变更登记**：r012 需求单 §10.1 的「交流页不挂大屏」由本轮改写，变更记录同步到 `docs/rounds/r012-superadmin-console/changes.md`（只加一行指路，不改历史结论）。

## 6. 风险与假设

1. **三人档焦点**可能不是布局 bug 而是「名册/轨道时序」——若复现显示是时序，修法则落在「等人在场再判焦点」（design §2 给两条路径），不影响 E1/E2 判据。
2. **强停共享**的耗时由 LiveKit Cloud 判离线决定（通常 10~15 秒），**这不是我们的 bug**：判据写成「如实记录数字」，若超过 10 秒我会在 review 里写明并给「无帧超时提示」的候选（不做，除非你要）。
3. **worker 自愈**治不了 FFI panic 本身；若 panic 发生在连接建立后（会话中），退出码路径同样兜住（守护脚本重启），但会丢该房当次转写——review 如实写。
4. **回看页**只读，不引入写入路径；权限默认值（在册成员可看）比 r012 更宽一档，**若你不认，我按 Q1 改回「仅房主/协管/超管」**。

### §10.5 断线重连真实中断级验收方案（E18b/E18c；本轮只出方案）

**目标**：用**真实中断**（不是事件注入）证明「断 8 秒 → 自动重连 → 设备 / 举手 / 焦点状态保持」，产出 5 项观察，闭合 r004 的 E18b/E18c。
**判定口径（五项）**：
a) 断后几秒状态条出现「正在重连…」、控制坞按钮是否变灰；
b) 断期间地址栏是否仍停在 `/rooms/<id>/live`（不回列表/登录页）；
c) 恢复后几秒自动回到「已连接」（不必点「重新连接」）；
d) 设备状态是否与断前一致（麦克风/摄像头 on/off 不变）；
e) 断前若该端持有焦点或举手，恢复后是否仍在（库里 `room_focus` / `room_hand_raises`，按库重取）。

**三种真断手段（按侵入性从低到高，逐个试，哪个真让 SDK 进重连态就用哪个）**：

| # | 手段 | 真断性质 | 侵入性 | 已知风险 |
| --- | --- | --- | --- | --- |
| ① | CDP `Network.emulateNetworkConditions(offline=true)` 8 秒后恢复 | 浏览器层网络离线（新请求失败） | 零（只动我起的隔离 Chrome） | r004 实测：8 秒窗口内 SDK **未**进重连态（既有 TCP/WS 未被切断）→ 预计无效，仍需实跑确认 |
| ② | 暂停浏览器进程 8 秒（`NtSuspendProcess`，只对隔离 Chrome 的进程树） | 客户端假死：心跳/ACK 停发 | 低（不动系统设置） | LiveKit Cloud 判离线耗时未知；恢复后是否自动回连需实测；若判「已断开」即落入 c 项边界（如实记） |
| ③ | 临时防火墙规则挡 LiveKit 出网 8 秒（`netsh advfirewall` 加规则 → 睡眠 → 删规则） | 最接近物理断网 | **中：需管理员 + 你批准动系统设置** | Cloud 多 IP，可能只挡部分；规则若残留会持续挡（脚本必须 try/finally 删） |

**执行顺序**：① → ② → ③（前两个全自动、零副作用；两个都无效才提 ③ 请你批，或退回你按 MV-1 手动关 Wi-Fi 8 秒）。
**载体**：新建 `frontend/scripts/verify-reconnect-drill.py`（隔离 Chrome + 五项观察自动记录 + 断电期间/恢复后截图 + 失败也如实输出），与既有三份自检脚本同风格。
**回填位**：`docs/rounds/r004-room-extras/review.md` E18b/E18c 行、`docs/00-requirements/r002-livekit-room.md` §4、`docs/rounds/r011-debt-backfill/manual-verification.md` MV-1。
**谁做**：①②由我跑；③或物理断网由你决定（你点 Wi-Fi 就用 MV-1 的四项填空表）。
**本轮状态**：**只出方案，不实施**（等你说「跑」）。

## 10.6 断线道具实测结果（2026-09-20，照实记）

按你要求做了「点一下断一个固定演示账号」的现场道具：`demo-window.bat`（受控窗口）+ `demo-disconnect.bat`
（点一下，`backend/scripts/demo_disconnect.py` 只冻那个窗口的**网络服务子进程** N 秒再恢复）。三次实测：

| 手段 | 结果 | 判断 |
| --- | --- | --- |
| 冻结整窗进程树（fallback） | 窗口卡住不渲染 → **台下看不到过程** | 不用作演示 |
| CDP `Network.emulateNetworkConditions(offline)` | 离线 18 秒期间该端仍显示「已连接」（既有 WS 未断），恢复后变「已断开」且**不自愈** | **不可用**（与 r004 记录一致） |
| **临时防火墙拦 LiveKit 出网**（首选，需管理员） | 干净基线一次：两端都在**断的过程中**进「正在重连…」（房主 **1.0 秒** / 被断端 **3.0 秒**），12 秒后删规则，两端 **17.1 / 18.1 秒**（即恢复后 5~6 秒）自己回「已连接」，**举手保持**、地址栏不变、规则无残留 | **首选**：`demo-firewall-cut.bat`（整机级阻断，两队窗口同时演） |
| 只冻**网络服务子进程**（免管理员备选） | 12 秒：恢复后 ~1.5 秒出「正在重连…」、~4.5 秒回「已连接」，**举手保持**；10 秒那一次恢复后停在「已断开」**未自愈** | **可用但不稳**（建议 12 秒 + 兜底话术） |

**前提（重要）**：防火墙法要求被演的两端**都先处于「已连接」**。一次基线不干净的运行里，房主端在断前就已经是「正在重连…」，阻断后它走到「已断开」并且 **30 秒内没有自己回来**——这既是道具的使用前提，也是一条产品观察：**已经处于降级状态的客户端会放弃重连**（是否要加「重新连接」引导或无上限重试，见 review §6 ⑦）。

边界：断的过程中被断端画面停在断前那一帧（Chrome 网络栈同样被冻）；台下的可见证据是**另一端的成员列表**
（实测断后约 2~3 秒该成员变「不在房间」）。要让「正在重连…」在断的过程中就出现在被断端，需网络层真阻断
（临时防火墙 / 物理断网，本页 §10.5 的手段③，**需你批准**）。另：三次实测中一次观察到**房主自己**在成员
列表里也短暂变「不在房间」（同一时刻两端都不活跃）——已登记为待复看项，未定性。

## 10.7 失焦 / 遮挡对连接的影响（2026-09-20 实测，你问的）

| 情形 | 页面状态 | 结果 |
| --- | --- | --- |
| 窗口**可见但失焦**（摆在屏幕上、不在最前） | `visibilityState=visible`、`document.hasFocus()=false` | **连接不受影响**：连续 40 秒失焦期间状态条一直「已连接」（一次小窗实测；离屏窗口在观察开始时也处于失焦且已连接） |
| 窗口**被 Chrome 判为 hidden**（屏幕外 / 最小化 / 切别的标签 / 被完全遮挡） | `visibilityState=hidden` | **5 秒内掉到「已断开」**，随后 60 秒**没有自愈**（三次轮询都停在终态） |

代码侧：前端**没有任何失焦/可见性主动断连逻辑**——`room.disconnect()` 只在三处被调用（离开房间 `RoomLivePage:314`、结束房间 `:332`、连接清理 `:248`）；`visibilitychange` 只用在 `usePresenceBeat`（在线心跳）与 `useRosterSync`（切回窗口重拉名册）。
后台化的其它副作用（都不是掉线）：轮询在后台不空跑（`useGlobalChat` 的 `refetchIntervalInBackground:false`，`main.tsx` 的 `refetchOnWindowFocus:true`）→ 系统消息/名册/大屏消息在你不看它时可能"看起来不动"，**切回窗口瞬间会补齐**。

**已修（r013 cp-11，你「不要这个隐藏断链」）**：
1. **根因（SDK 源码）**：`livekit-client` 的 `roomOptionDefaults.disconnectOnPageLeave = true` 会挂 `pagehide`/`beforeunload`，而 `window.addEventListener('freeze', onPageLeave)` 是**无条件**挂的 —— Chrome 冻结隐藏/离屏页面时派发 `freeze`，SDK 就 `disconnect()`，且归因走 `ClientInitiated`（原因文案为 null，看起来像「自己离开」），自愈也没有。
2. **应用侧修**：`useRoomConnection` 自己监听 `freeze`/`pagehide` 记一笔，把这类断开与「用户点离开」区分开（给文案「页面被浏览器挂起…」并暴露 `autoDisconnected`）；`RoomLivePage` 在页面回到可见时**自动重连**（最多 3 次退避），失败则显示已有的「重新连接」banner。实测：CDP 确定性冻结 → 解冻后 4.0 秒仍「已断开」→ 5.5 秒「正在连接…」→ **8.5 秒「已连接」（自愈成立）**。
   （未复现项：那次「页面被浏览器挂起」的文案没出现 —— 断开可能走的不是 freeze 事件路径；文案与归因留待下一轮复看。）
3. **演示窗口侧修**：`demo-window.bat` 加 `--disable-features=CalculateNativeWinOcclusion --disable-backgrounding-occluded-windows --disable-renderer-backgrounding --disable-background-timer-throttling`。实测：离屏 **45 秒**全程 `visibilityState=visible`、状态条一直「已连接」。

演示口径：用 `demo-window.bat` 开的窗口最稳；用你自己的窗口就摆屏幕上、别最小化/别移出屏幕/别切标签。

## 10.8 口径升级：「界面不管怎样都不许断开」（2026-09-20 你的要求）

**新口径**：非用户主动的中断，界面**一律不显示「已断开」**，按「正在重连…」处理，并由页面层**不限次数**重连直到回来；只有三条真终态才落「已断开」并给原因：被移出（PARTICIPANT_REMOVED）、房间结束（ROOM_DELETED/ROOM_CLOSED）、同账号在别处进入（DUPLICATE_IDENTITY）。用户自己点「离开房间/结束房间」照旧不进自愈。

实现（cp-14）：
- `useRoomConnection`：`onDisconnected` 重排判定 —— 先排「用户离开 / 真终态」，其余（`CLIENT_INITIATED`、无原因、浏览器 freeze/pagehide、网络中断）统一置为 `reconnecting` + `autoDisconnected`，不再落 `closed`；重连过程中的失败也保持 `reconnecting`（不再把界面打成「已断开」）；新增 `recoverable` 供页面层判定。
- `RoomLivePage`：自愈循环改为**不限次数**（票每次现签、退避上限 4 秒），触发点 = 进入可恢复态 + `visibilitychange` + `resume` + 每 5 秒兜底；连接对象放进 ref，effect 只依赖 `recoverable`（否则会被反复 cleanup 掐死循环，这是本轮实测踩到的真 bug）。
- 实测（真机，同一窗口）：连续 4 次把实时连接掐断 → **界面一次都没出现「已断开」**，每次自动恢复 **7.3 / 7.9 / 7.9 / 11.0 秒**，恢复后格子在、举手/焦点照旧。

已知边界（照实登记）：
- 恢复要 7~11 秒，原因是 SDK 不允许**同一个 Room 实例**在 `disconnect()` 后立刻重连（实测抛 `ConnectionError: Client initiated disconnect`，要等内部结算完才放行）。试过「换新 Room 实例」的改法（理论上 2~4 秒），实测**把初次连接也带坏了**，已回退；正解是「恢复时换实例 + 监听重挂载」的重构，留下一轮做。
- 网络层中断（防火墙掐断那种）走的是 SDK 内部重连，恢复 **5~6 秒**、且过程中不经过 `closed`（见 §10.6），比上面这条快。
