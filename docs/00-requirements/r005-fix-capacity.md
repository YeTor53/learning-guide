## 1. 目的

「房间人数上限」是**我们自己的房间规则**，不是音视频服务的能力参数。本轮把人数判定从 LiveKit 迁回本库：**以在册成员数为唯一权威**，让列表卡、交流页、准入三处说同一个数；并让成员增减这类**房间事件**在消息列表里留痕（你说「这种房间事件都可以进消息列表」）。

## 2. 边界

- **要做**：① 容量口径 = 本库 `room_members.status='active'` 计数（在册）② 满员时**申请直接拒**（409 `ROOM_FULL`）、**批准也拦**（防并发超员）③ 取票不再查 LiveKit → 顺带修掉取票 0.8~1.8 秒的外部调用 ④ 房间事件写系统消息 ⑤ 前端把三处文案统一到「在册 / 容量」。
- **不做**：不引入排队实体、不做占座超时、不改房间生命周期其余条款、不改音视频能力（LiveKit 只管承载）、不给举手/焦点等 r004 事件加系统消息（本轮只房间成员事件）。
- **不引入新错误码**：复用既有 `ROOM_FULL`。

## 4. 口径与规则（实现事实源见 design.md）

1. **容量唯一权威**：`count_active_members(room) = count(room_members where status='active')`；上限 = `rooms.capacity`（默认 8）。
2. **判定点（三处，全在库内、同一事务、锁房间行）**：
   - `POST /rooms/{id}/join-requests`（`request_join`）：在册 ≥ 容量 → **409 `ROOM_FULL`**（新增拦截，替代 ADR-0012 D2 的「申请不校验」）
   - `POST /join-requests/{id}/approve`（`approve_join_request`）：批准前再查 → 满 → **409 `ROOM_FULL`**（不加不变量：在册永远 ≤ 容量）
   - `POST /rooms/{id}/token`（`issue_room_token`）：**移除 LiveKit 查询**；在册即放行（非在册 403、结束 409 不变）
3. **不变量**：任何时刻 `在册成员数 ≤ capacity`（用例 + smoke 断言）。
4. **三处显示同一口径**：列表卡（已是 `memberCount/capacity`，语义确认为「在册/容量」，满员加「已满」态）、交流页状态条（由「在场/容量」改为「在册/容量」）、成员抽屉（在房间里 / 不在房间 的在线标记**保留**，那是 LiveKit 事件驱动的「此刻在不在」，与容量无关）。
5. **房间事件进消息列表**：写 `chat_messages`（`kind='system'`，`user_id` = 触发者），与状态变更**同一事务**：

| 事件 | 触发点 | 文案（正文） |
| --- | --- | --- |
| 满员拒绝 | `request_join` 命中满员 | `房间已满（上限 {capacity} 人），本次申请未通过` |
| 成员加入 | `approve_join_request` 成功 | `{displayName} 加入了房间` |
| 成员离开 | `leave_room` 成功 | `{displayName} 离开了房间` |
| 成员被移出 | `kick_member` 成功 | `{displayName} 被移出房间` |
| 房主移交 | `transfer_host` 成功 | `{displayName} 成为房主` |
| 房间结束 | `end_room` 成功 | `房间已结束` |

（前端**无需改动**：`.chat-system` 居中灰字已支持 `kind='system'`。）

## 7. 风险

1. **Q2 的「校验失败拒绝」在名册口径下没有触发场景**：容量判定变成库内 SQL 后不存在外部失败；本轮的处置是 —— ① 不引入 `CAPACITY_CHECK_UNAVAILABLE` ② 在 design 里写明「若将来重新引入外部判定，必须 fail-closed」③ 若你要求保留 503 语义，请在批复里指出（否则按此执行）。
2. **ADR-0012 的 D1/D2/D3/D5/D8 被本轮的 ADR-0016 修订**：已合并的 ADR 不回改正文，只在 `ADR-0012` 追加一行「被 ADR-0016 修订」并指向新 ADR（append-only）。
3. **在场 ≠ 在册**：可能出现「在册 8 人但只有 3 人在线」；此时第 9 人**申请被拒**（因为名额已占满）。这是 Q1=2 的直接后果，需在功能页与教学页写清楚。
4. **分支基线**：r004 已由你合并进 `main`（`daf7696` Merge branch 'req/r004-room-extras'，tag `round-r004-done` 已打）。本分支 `req/r005-fix-capacity` 直接从该 `main` 拉出，无叠加依赖。
