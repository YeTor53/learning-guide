范围：r004（M3）房内四种新能力（消息 / 举手 / 焦点 / 共享）的实时层。
相关：`docs/01-architecture/r004-realtime-extras-architecture.md`、`docs/rounds/r004-room-extras/design.md` §6、ADR-0011（实时在场模型）。

## 决策

1. **HTTP 是唯一真相源**：任何用户可见的业务状态（消息、举手、焦点）都必须能从库里查出来；写操作一律走 HTTP，落库成功才算成功。
2. **LiveKit Data Channel 只做房内加速**：写成功后由发起端广播全量快照/新消息，让其他端「立刻看到」。
3. **不引入 WebSocket 服务**（不新增依赖、不改运行形态）。
4. **重连与刷新必须 `refresh()`**：连接成功或页面刷新后，用 HTTP 重新拉取消息/举手/焦点，再订阅通道 —— 保证「只靠广播才能看到的状态」不存在。
5. **快照收敛规则**：举手与焦点用「全量快照 + 时间戳（`at` 大者胜）」，消息用「服务端 `id` 去重 + `createdAt` 排序」。

## 理由

- 我们的后端**不在 LiveKit 房间里**（它只签发 Token 与做管控），所以 Data Channel 的消息**服务端收不到** —— 想落库就必须有 HTTP 这条腿；
- 演示验收里最硬的一条是「**刷新/重进后与库一致**」。把库当真相，这条验收天然成立；反过来（广播当真相）就需要在客户端做持久化与冲突解决，成本远高于收益；
- 自建 WebSocket 会带来连接鉴权、心跳、多实例广播（Redis/消息总线）、部署形态等一串新面 —— 对单人 4 天窗口的项目是明确的过度设计；
- 纯轮询（3~5 秒）会让「实时讨论」的观感垮掉，且演示时最容易被看出延迟。

## 后果

**好处**：零新依赖；刷新即一致；多实例部署无状态问题；每条能力都能被 pytest 覆盖（HTTP 面）。
**代价（如实）**：广播是「尽力而为」——掉线的人会错过即时通知（由 `refresh()` 兜底）；广播链路本身的可靠性依赖 LiveKit（Cloud 模式下可用性很好，自建模式是本地进程）。
**明确不做**：消息的离线推送、跨房间通知、已读回执（M5 或不做）。

## 备选与否决理由

| 备选 | 否决理由 |
| --- | --- |
| 自建 WebSocket 作为真相通道 | 新依赖 + 鉴权/多实例/部署复杂度；与「4 天窗口」不匹配 |
| 纯轮询 | 演示观感差（3~5 秒延迟），且轮询频率上去后与 WebSocket 的成本差距缩小 |
| 广播当真相 + 本地持久化 | 需要客户端冲突解决；「刷新与库一致」的验收会变得脆弱 |
