# ADR-0012：房间 = 一次性讨论；等候用「申请列表」，不另建队列

## 背景

实现期发现：容量按「在册成员」计数、界面与用词把「成员」当长期名册讲，读起来像常设小组，与术语表「房间 = **一次讨论**的容器」、README「房间结束后的纪要」、r001 已验收的 `ended` 终态相矛盾（详见 `docs/rounds/r002-livekit/redirect-05.md`）。用户拍板：**选 A（一次性讨论）**，并追问「等待排队的情况你打算怎么处理」。

## 结论（9 条）

1. **房间 = 一场讨论**：`active → ended`，`ended` 为终态、只读回访（纪要 / 出席快照的载体）。**不可重开**：要再讨论一次 = 新建房间（M3 可加「复制房间再开一次」入口，不进本轮）。
2. **在册即占座**：座位 = `room_members.status = 'active'` 的行；`在场 + 已批准未入场 = 在册`。三张表结构不变。
3. **退场即释放座位**（已实现，实现期实测确认）：离开（`self_leave`）、被移出（`kicked`）都会把该行置 `inactive`，`count_active_members` 随即下降，名额立刻可用；**不是**等到房间结束才释放（`redirect-05` 里 P1 的旧表述已更正）。
4. **未入场者占座**：批准即发座位（保证被批准的人进得来）。代价是「房里看着不满也进不去」；补偿手段是房主可**移出**未入场者清位（已有能力）。占座超时自动失效 → backlog（M5）。
5. **等候 = 等待页 + 申请列表**（不新建队列实体、不新增错误码）。~~满员时申请仍可提交、批准受容量限制~~ → **已被下方修订 D2/D3/D4 取代**（实测 r001 的 `request_join` **也**拦容量，满员根本进不了队列）。
6. **排队顺序由房主决定**：申请列表按提交时间排序，但**不自动放行**（自动批准最先申请者需要服务端主动机制 + 通知通道）→ backlog（M5）。当前口径：谁被批准谁入场，排序判断由房主承担。
7. **满员时的两处呈现**：① 房主侧申请区块显示「已满 N/N · 先移出或结束房间」；② 申请人侧等待页第二态「房间满了，正在等一个座位」（与「等房主批准」同一页、同一 5 秒轮询，获批即自动进入）。
8. **角色随讨论生效**：房主 = 创建者；协管 = 本场授权；散会（`ended`）后都不再有效（历史保留，供回访展示）。
9. **房间老化**：`active` 房间不会自己结束（三个月后仍可进）→ 登记 backlog（与 M5 定时校准一起做）。

## 被否方案

| 方案 | 否掉的理由 |
| --- | --- |
| 引入 `sessions`（场次）表，房间可开多场 | 违背术语表既有定义；r001 已验收的 9 条接口与验收大部分要重写；本轮等于推倒重来 |
| 新建 `queue` 表 + 自动放行 + 推送通知 | 需要服务端常驻机制与跨页通知通道（M5 才有）；8 人学习讨论室里「房主点批准」更简单可控 |
| 不占座（谁先到谁坐，批准不保证有位） | 会出现「被批准了却进不来」的失信体验 |
| 满员时禁止提交申请 | 门口的人失去排队能力，房主也看不到需求；现状（申请保留）更符合等候室语义 |

## 修订（2026-09-18，用户口径；实现随 cp-r002-4 一起落地）

> 用户原话：「不要未入场，申请之后进等待室，申请允许后直接进入，失败回到主界面，不要有手动加入这一步。」

| 编号 | 修订后的口径 |
| --- | --- |
| D1 | **容量 = 在场**（LiveKit 实测连接数），**不再按在册算**；取消「未入场占座」这个概念 |
| D2 | **申请不校验容量**（删除 r001 在 `request_join` 里的 `ROOM_FULL` 拦截）：申请人总能进等待室，随时可撤回 |
| D3 | **批准不校验容量**（删除 `approve_join_request` 的容量拦截）：批准 = 授予本场入场资格；房主侧申请区块显示「在场 N / capacity」供判断 |
| D4 | **批准后自动进入**：等待页 5 秒轮询发现「已批准」→ 自动取票并连接 → 直接进交流页；**没有手动点「进入房间」这一步** |
| D5 | **容量闸唯一在取票**（`POST /api/rooms/{id}/token`）：`在场 >= capacity` → 409 `ROOM_FULL`；外部查询失败时**降级放行**（不因监控失败拦截用户），由 Token 的 `max_participants` 兜底 |
| D6 | **失败回主界面**：等待页遇到 `ROOM_FULL` / `ROOM_ENDED` / 网络失败 → 原地显示原因 3 秒 → 自动回房间列表页（主界面），不留在半吊子状态 |
| D7 | **重进而非「加入」**：在册成员（曾入场）从管理页用「回到讨论」重进；从未入场过的人只有「申请加入」→ 等待页 → 自动进入。**没有手动「加入」** |
| **D9（2026-09-19，被 r005 ADR-0016 取代）** | 本节 D1/D2/D3/D5 关于「容量 = 在场 / 申请与批准不校验容量 / 容量闸唯一在取票且失败降级放行」的条款，已被 `docs/03-decisions/r005-adr-0016-room-capacity-membership.md` **修订为「容量 = 在册成员（库为权威）」**；正文保持原文不改，仅在此追加指路 |
| D8 | 术语修订：**座位 = 在场**；**在册** = 本场已获准（含尚未入场的人，但不再占座、界面不单独呈现）；删掉「未入场占座」表述 |

**实现清单（cp-r002-4 一起做）**：`services/rooms.py` 删两处容量拦截 + `issue_room_token` 增在场校验（用 `livekit.list_participant_identities`）→ 接口用例转正（去掉 xfail）→ 等待页两态与自动进入 → 管理页按钮口径（申请加入 / 回到讨论）→ 功能页 F-13/F-17、按钮矩阵、需求单 Q12 与验收同步。

## 影响

- **代码**：本轮**无需改容量规则**（现状已是在册占座 + 退场释放）；要做的是①满员时的文案与提示（房主侧申请区块、申请人交流页提示）、②等待页第二态（cp-r002-4）、③术语与文案把「成员」改为「出席 / 在册」口径。
- **文档**：术语表（+在册 / 座位 / 等候队列）、功能页 F-13/F-17、实现页 §8.1、需求单 Q12 与验收、roadmap backlog。
- **验收**：新增用例 2 条（满员时申请仍可提交且保留 `pending`；有人退场后同一申请可批准成功）；演示脚本第 9 步沿用（被踢者再申请 → 再批准重进）。
