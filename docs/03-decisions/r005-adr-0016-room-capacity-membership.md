<!-- overview -->
修订对象：`docs/03-decisions/r002-adr-0012-room-lifecycle.md` 的修订项 D1（容量=在场）、D2（申请不校验容量）、D3（批准不校验容量）、D5（容量闸唯一在取票且失败降级放行）。
本 ADR 由 r005 `cp-0` 提出，用户 2026-09-19 批复「**不要以 livekit 为准，那个只是房间使用的工具，人数上限等等是为房间服务的**」→ `status: accepted`。

## 1. 决定

1. **人数权威 = 本库 `room_members.status='active'` 计数**（「在册」= 本场已获准的人）；上限 = `rooms.capacity`。
2. **判定点回到库内三处**：申请（满 → 409 `ROOM_FULL`）、批准（满 → 409）、取票（**不再查 LiveKit**，在册即放行）。
3. **不变量**：提交后 `在册 ≤ capacity`（由 `lock_room` + 同事务判定保证）。
4. **LiveKit 的 `max_participants`** 降级为「音视频承载兜底」，不再是人数权威。
5. **房间事件留痕**：满员拒绝、加入、离开、被移出、移交、结束六类事件写 `chat_messages(kind='system')`，与状态变更同事务。

## 2. 为什么

- 容量是**业务规则**（这间房安排多少人讨论），不该由承载工具的运行时状态决定；工具换掉（自建/云）不应改变房间规则。
- 旧口径（取票时问 LiveKit）有三个后果：① 取票路径里一次 0.8~1.8 秒的外部调用（实测，用户能感知的「连上服务慢」）② 查询失败时**降级放行**（人数限制形同虚设）③ 显示与准入口径不一致（列表卡写在册、准入看在场的「8/8 还能进」）。

## 3. 考虑过的替代方案

| 方案 | 否决理由 |
| --- | --- |
| 保持「容量 = 在场」（ADR-0012 D1）并只修显示 | 显示要真实在场数就得对每个房间查 LiveKit（更慢）；且失败降级的洞仍在 |
| 双闸：名册封顶 + 在场兜底，两处都显示 | 两个真相源，必再出现「两处数字不一样」；用户明确要「同一口径」 |
| 在场为准但 fail-closed | 仍把业务规则绑在承载工具上；且每次取票都要外部调用 |

## 4. 后果

- 正面：三处（列表卡 / 状态条 / 准入）同一数字；取票从 ~1650ms 降到库内查询级；行为可预期（不会因外部抖动而放人）。
- 负面（须写进功能页与教学页）：**可能「在册满员但房内只有几人在线」** —— 名额被已获准的人占着，第 9 人要等有人离开才能申请。
- 兼容性：已存在的超容量房间（如演示库里某房间在册 9~11 人）**不会被自动清理**；表现为「已满且暂时无人能进」。是否清理属运维，见 r005 需求单 §7。
