<!-- overview -->
r002 第一次把**外部实时服务**接进本项目，随之出现一批会长期影响代码与文档的约定（身份、在场、失败面、重连）。
本 ADR 把这些约定固定成可引用的条目，供实现、审查与后续轮次（M3 的举手/焦点、M5 的断线判定）直接引用，避免每轮重新论证。
状态：`proposed` —— 随 r002 需求单一起待你批准；批准后转 `accepted`。

## 背景

- M1（r001）已有「成员身份」这一持久事实源（`room_members`）与房间生命周期；M2 引入 LiveKit 后多出「此刻谁连着」这一**瞬时**事实源，两者会不一致（断线残留约 15 秒、关标签页、切网络）。
- 交付要求把「服务端踢人」（移除 Token 权限并强制断开）列为硬要求，意味着踢人必须真的作用在实时层，而不只是改库。
- 外部服务会失败（不可达、超时、额度用尽），而业务动作（踢人、结束房间）在用户意图上已经成立。

## 决定

| # | 约定 | 理由 |
| --- | --- | --- |
| 1a | **界面用词与库口径必须分开**：库里的 `room_members.status = active/inactive` 是**身份口径**（成员身份是否有效，退出原因在 `exit_reason`）；界面的「活跃 / 非活跃」是**在场口径**（此刻在不在房间里）。同一份成员列表按在场口径分两组（活跃 = 在房间里、非活跃 = 不在房间内），状态条人数用**在场人数**（`N / 8 在房间`）。禁止把两个口径混用成「成员数 = 在场数」 | 两套口径同源不同义，混用会让人数与名单自相矛盾（第一版实测：状态条 2/8 但房里只有 1 人） |
| 1 | **双事实源**：成员以 PostgreSQL 为唯一事实源，在场以 LiveKit 为唯一事实源；房内页把两者**求交**展示（在线/离线），**门禁只认库** | 在场不可靠（断线残留、切网、切后台），不能承载授权；库不能反映瞬时状态 |
| 2 | **identity = `user_id`**，不嵌随机后缀 → **不支持同账号真双开**；第二窗口进入会让先进入的连接被 `DUPLICATE_IDENTITY` 踢掉，界面提示「同一账号已在别处进入本房间」 | 成员/申请/踢人的键都是 `user_id`；双开会让「一个人两条成员记录」的假象污染权限判定。演示用两个账号 |
| 3 | **Token 无状态**：不进库、不缓存，每次连接现签；TTL 由 `LIVEKIT_MODE` 派生（`cloud` 3600s / `self` 300s），不新增环境变量。**TTL = 这张凭证的保质期**：LiveKit 只在握手时校验签名与有效期，没有「吊销名单」；`cloud` 用 `revoke_token_ts` 可立即作废旧票，`self` 没有该能力 → 只能把保质期压短（300s），把「被踢后还能拿旧票重连」的窗口压到 ≤5 分钟；代价是长时间停留 / 重连前要现签，而本项目每次连接本来就现签，正好规避（签名是本地运算，无网络成本）。** TTL 下限 60 秒**（不取更短）：票必须在「取票 → 服务端握手成功」之间保持有效，而这段耗时包含 ICE/媒体协商（约 1~3 秒）以及用户面对浏览器设备授权弹窗的停留（常见 5~15 秒），还要留出签发端与 LiveKit 服务器的时钟偏差余量；TTL 压到与握手同量级（如 10 秒）会让「票在手却连不上」成为常态，且网络抖动触发的全量重连需要重新握手（官方口径：全量重连等同「离开房间再回来」）→ 短票会把正常用户也挡在门外。若将来要把票做得更短，前提是改用官方 `TokenSource` 模式（服务端 token 端点 + 缓存 + 自动续签），本项目当前是手动 `Room.connect`，无自动续签 → 不适合短票 | 减少一处状态与失效面；自建模式无法撤销 Token，只能靠短 TTL 兜底（ADR-0003） |
| 4 | **踢人 = 库先落地 + 提交后断线**：事务内把目标成员置 `inactive/kicked`；**事务提交后**调 `RemoveParticipant`（Cloud 带 `revoke_token_ts`）；外部调用失败只记日志，接口仍 200 并在响应里带 `livekitApplied` | 用户意图已在库内成立；外部超时不应回滚业务状态，也不应拖住数据库连接 |
| 5 | **结束房间 = 原有三件事 + 提交后 `DeleteRoom`**：库侧（`ended` / 成员 `room_ended` / 申请 `cancelled`）不变；实时断开是对外效果 | 同 4；且「房间是否结束」由 Host 显式决定，与 LiveKit 的空置超时无关 |
| 6 | **断线归因以 SDK `DisconnectReason` 为准**（`PARTICIPANT_REMOVED` / `ROOM_DELETED` / `DUPLICATE_IDENTITY` / `CLIENT_INITIATED` …），「再取一次 Token」只作兜底 | 原因由 SDK 直接给出，少一次往返且更准；网络真断时根本取不到 Token |
| 7 | **重连分层**：连接层（SDK 自动重连 + 界面「正在重连…」/已恢复）与设备层（麦克风/摄像头开关在重连后保持）**属本项目的实时房间基本体验**；业务状态（举手/焦点/共享/群聊）恢复留 M3/M5；**重连不改库** | 自动重连是 SDK 内建能力，不写进设计等于把「网络抖 5 秒」做成「掉线重进」；业务状态依赖 M3 才存在的能力 |
| 8 | **唯一出口**：只有 `app/services/livekit.py` 接触 LiveKit 与 `LIVEKIT_*`；`async` 只在该模块的 `_run()` 一处出现；密钥不进前端/产物/日志/错误响应 | 与架构页 §3 的分层硬约束一致；密钥纪律是交付硬扣分项 |
| 10a | **准入判定与准入执行分开看**：前端「隐藏页 / 等待页 + 先取票再连接」属于**准入判定（UX 门）**，由我们的前端与后端执行，能拦住一切「经由我们的客户端」的进入（名单、成员状态、房间状态都在这层生效）；但它**不是安全边界**——客户端只要手里有一张仍在有效期的票，就可以绕开我们的页面直接连 LiveKit。真正的**准入执行**在平台侧（Cloud 的 `revoke_token_ts`）或靠短 TTL（自建）。两层各管一段，缺一不可；若要求「每次进入都必须由后端点头」，需要一次性 `jti` + 服务端登记（属过度设计，登记 backlog） | 判定与执行的位置不同，混为一谈会得出「加了隐藏页就安全了」的错误结论 |
| 10 | **不做应用层封禁名单（banned list）**：LiveKit **没有「入房授权钩子」**（Webhook 只是事后通知，不能拒绝入房），所以只存在我们库里的名单**拦不住「拿旧票直接连 LiveKit」**——那个人根本不经过我们的后端。本轮按官方对自建的写法处理（短 TTL + 移除后不再签发）；「封禁」（长期禁入）若要做属后续轮次功能：必须**签发侧强制** + Cloud 侧 `revoke_token_ts` 作废旧票 + 解除与审计，且会与 r001 已定的「被踢者可立即再申请」（FQ-3）冲突，需按 L3 走 | 名单的位置决定了它的效力边界：裁决在平台侧，不在我们库里 |
| 9 | **8 人上限单一口径**：以 `ROOM_CAPACITY`（默认 8）为准，在申请/批准阶段拒绝（`ROOM_FULL`）；Token 内 `RoomConfiguration.max_participants` 只作兜底，**不用在场人数做门禁** | 口径单点；在场数抖动会误拒 |

## 被否方案

| 方案 | 否决理由 |
| --- | --- |
| 用 Cloud Webhook（`participant_left` 等）驱动成员状态 / 断线判定 | 需要公网可达回调地址与签名校验，本地演示环境不具备；留 M5 再评估 |
| 以在场状态反写库成员（断线即 `inactive`） | 断线残留十几秒会把「切网」误判成「离开」，且与「房主清位」的人工兜底冲突 |
| 允许同账号真双开（identity 加随机后缀） | 与前 8 条之外的权限判定、成员唯一性、踢人目标（按 `user_id`）全部冲突，收益不过是多开一个窗口 |
| 用 `@livekit/components-styles` 默认主题 + 现成页面 | 与 ADR-0008 的视觉体系冲突；交付要求明确不得使用 LiveKit Meet 默认页面 |
| 在事务内调用 LiveKit 管控接口 | 外部超时会占住数据库连接与行锁，失败还会连带回滚已经成立的业务意图 |

## 影响与后果

- 演示与验收：必须用**两个不同账号**；断网重连的可观察证据是「徽标转『正在重连…』→ 自动回『已连接』」且库内成员表不变。
- 自建（`LIVEKIT_MODE=self`）模式下踢人的说法只能是「断开 + 短 TTL + 拒绝再签发」，验收与文案都按此如实表述（ADR-0003 已定）。
- 后续轮次：M3 的举手/焦点/共享需自己设计「重连后如何恢复」（M5 ① 已登记）；M5 若引入 Webhook，第 1 条与第 6 条需重评。
