## 1. 目标与边界

**目标**：结束不是终点，而是「归档」的起点 —— 每个参与过的人都能在结束后找到这间房，看到它的**最终快照**（信息 / 成员 / 申请 / 消息 / 纪要），房主还能对它做有限的管理动作（目前只考虑「删除归档」一项待拍）。

**不做**（硬边界）

- 重开已结束房间、恢复成员、继续发言（ADR-0012：房间 = 一场讨论，`ended` 是终态）；
- 修改历史（成员快照、申请结论、消息内容一律只读）；
- 公开分享 / 匿名访问（默认只对参与过的人可见；要公开得另开一轮并重做口径）；
- 全文搜索、跨房间统计、导出 PDF（M5 增量）。

## 2. 术语与状态

- **归档（archive）= 结束后房间的只读产品视图**，不是新状态：归档里的房间在库里仍是 `status='ended'`。
- 状态机不变：`active` →（房主结束）→ `ended`（终态）→ 归档视图可见；另设「隐藏」为**个人或房主视图标记**（若要，见 §7）。
- 「归档」与「回看」的用词纪律：界面统一说**归档**、动作用**查看归档**；禁用「回看房间 / 回到房间」（会暗示可以重进，与一次性讨论口径冲突）。

## 3. 谁看什么（权限矩阵）

| 角色 | 能看到 | 看不到 / 不能做 |
| --- | --- | --- |
| 曾参与（含主动离开、被移出、房间结束） | 房间信息（标题/主题/简介/房间码/结束时间/在房时长）、成员快照（角色 + 退出原因 + 加入时间）、申请历史（全部状态）、消息记录、纪要；导出（若做，见 §12 A6） | 任何写入动作：申请、批准、踢人、改角色、结束房间、发消息 |
| 房主 | 同上 + 纪要重新生成（M4 `S-1`）；「删除归档」待拍（§12 A4） | 不能改历史、不能重开 |
| 登录但从未参与 | 列表页仍能看到「已结束」徽标（现状），**归档内容不可见**（隐私默认闭合） | 归档详情 403 或 404 |
| 未登录 | 看不到归档入口（引导登录） | — |

> 这条例外值得单独记住：现在的 `GET /api/rooms/{id}` 对「非活跃成员」直接 403。归档要求**「曾是成员」也能读**，属于**对外可见面的变化（L3）**，必须在 M4 的需求单里写死。

### 3.1 「离开即截止」——可见内容的时间窗口（用户 2026-09-19 补充口径）

> 原话：「但是数据截至至他离开」（批复 A2=① 时补充）

- **规则**：读者能看到的归档内容，截止到**他离开那一刻**：
  `可见窗口 = [房间创建, min(房间 ended_at, 我的 left_at)]`（从未离开且房间已结束 → 完整）。
- **按块落地**：

| 块 | 已离开的读者 | 一直在册的成员 / 房主 |
| --- | --- | --- |
| ① 头部（标题/主题/房主/结束时间/在房时长） | **完整可见**（房间级事实，不含他人内容；本项目不支持改名） | 完整 |
| ② 纪要 | 待拍（§12 A8）：整场纪要含他离开后的内容 | 完整 |
| ③ 成员快照 | 只显示 `joined_at <= 我的 left_at` 的成员，且其状态/退出原因按当时口径（不含之后加入的人） | 完整 |
| ④ 申请历史 | 只显示 `created_at <= 我的 left_at` 的申请及其当时状态（之后的批准/拒绝/撤回不可见） | 完整 |
| ⑤ 消息记录 | 只显示 `created_at <= 我的 left_at` 的消息 | 完整 |
- **提示**：页面顶部一条中性提示「你已离开这间房，以下内容截至 `2026-09-19 21:30`」；不显示「有 N 条你看不到」这类计数（等于泄露存在性）。
- **实现含义**：截断在**服务端**做（不是前端隐藏），且是 `get_archive_detail` 的一条统一规则；`was_member` 只判「能不能进」，截断判「能看到多少」。

## 4. 承载形态（三选项对比）

| 选项 | 是什么 | 优点 | 代价 |
| --- | --- | --- | --- |
| **A** 单房间归档页 `/rooms/:id/archive` | 一间房的完整只读快照 | 信息最全、可深读、可分享链接（给参与者） | 需要新页面与新路由 |
| **B** 归档总览页 `/archive` | 跨房间的归档索引（我参与的 / 我建的 / 主题 / 时间） | 找得到、可排序检索、给「归档」一个自己的空间 | 需要新页面 + 一个列表接口 |
| **C** 列表页卡片就地展开只读面板 | 零跳转 | 改动最小 | 信息受限、且与列表页「发现新讨论」的定位相互稀释 |

**推荐：B + A**（B 作入口，A 作详情），并把列表页 `ended` 卡片的动作从「无动作」改为**「查看归档」**（一步直达 A）。
理由：列表页的职责是发现；归档的价值是**在需要时找回来**，它需要自己的空间与筛选能力；C 只适合做临时兜底，不建议作为长期形态。

## 6. 接口与函数级草案

| 方法 | 路径 | 谁能调 | 请求 / 响应 |
| --- | --- | --- | --- |
| GET | `/api/archive` | 登录；**只返回自己参与过的** | `?scope=mine\|hosted&topic=&limit=&offset=` → `{items: ArchiveItemVO[], total, limit, offset}` |
| GET | `/api/rooms/{room_id}/archive` | **曾是成员**（§3 的 L3 变化） | → `ArchiveDetailVO = {room, members, requests, messages, summary\|null}` |
| DELETE | `/api/rooms/{room_id}/archive` | 房主（A4=② / A9=③） | 软删：写 `archived_hidden_at`，**不动 `rooms.status`、不删任何数据**；对成员/其他所有人不可见，房主自己仍可见并可恢复。**二次确认文案必须写明**：「删除后这个归档不再受保护，可能在必要时被清理，届时无法恢复。」 |
| POST | `/api/rooms/{room_id}/archive/restore` | 房主 | 撤销软删（清空 `archived_hidden_at`）。**尽力而为**：若数据已被清理 → 410 `ARCHIVE_PURGED`，前端提示「该归档已被清理，无法恢复」 |

> **软删需要的存储**（A4=② 的代价，见 §7）：`rooms.archived_hidden_at timestamptz NULL`（房主软删时间；`NULL` = 正常可见）——这是本设计**唯一确定需要的一条迁移**。
>
> **数据保护口径（A9=③ 拍板，必须写进 M4 的文档与界面）**：软删 = 房主主动让这条归档**退出保护范围**。
> - 库里数据**不立即删除**（否则「恢复」在语义上不成立）；
> - 但**不承诺任何保留期**：容量、合规或演示环境重置等需要时，软删的归档**可以被清理**（清理策略与执行时机属运维/后续轮次，M4 只需保证「软删的归档永远不在任何『保证保留』清单里」）；
> - 因此「恢复」是**尽力而为**：数据还在就能恢复，已被清理就走 `ARCHIVE_PURGED` 的明确失败；
> - 未被软删的 `ended` 房间**不在此条款内**（正常归档照旧保留）。

`ArchiveItemVO = {roomId, title, topic, topicLabel, endedAt, memberCount, myRole, summaryStatus}`

| 函数（后端） | 签名 | 职责 |
| --- | --- | --- |
| `list_archived_rooms` | `(conn, actor: UserVO, scope: str, topic: str \| None, limit: int, offset: int) -> tuple[list[ArchiveItemVO], int]` | `status='ended'` + 参与者过滤（`room_members.user_id = actor.id`，`scope='hosted'` 时再加 `role='host'`）；`ORDER BY ended_at DESC`；`total` 用同条件的 `count(*)` |
| `was_member` | `(conn, actor: UserVO, room_id: str) -> bool` | `EXISTS(SELECT 1 FROM room_members WHERE room_id=? AND user_id=?)`（含 `inactive` 行）——权限放宽的**唯一判据**，不许在路由层各写一遍 |
| `get_archive_detail` | `(conn, actor: UserVO, room_id: str) -> ArchiveDetailVO` | `was_member` 且未被软删（房主除外，房主可见自己的软删房）→ 取 `visible_until = min(room.ended_at, actor 的 room_members.left_at or ∞)` → 复用现有详情装配但**按 `visible_until` 过滤 messages / members / requests**（§3.1）→ 再挂 `summary`；房间 `active` 时返回 `ROOM_ACTIVE` |
| `visible_until_for` | `(conn, actor: UserVO, room_id: str) -> datetime` | 截断窗口的**唯一判据**（§3.1）：`LEFT JOIN room_members` 取该人的 `left_at`；`left_at IS NULL` 且房间已结束 → 取 `ended_at` |

| 组件（前端） | 位置 / 签名 | 职责 | 复用 |
| --- | --- | --- | --- |
| `ArchivePage` | `frontend/src/pages/ArchivePage.tsx` | 归档总览（筛选 + 行列表 + 分页 + 空态） | `useRooms` 风格改为 `useArchive` |
| `RoomArchivePage` | `frontend/src/pages/RoomArchivePage.tsx` | 单房间归档六块 | 只读消息块、成员行、`MarkdownLite`（M4） |

## 7. 数据与迁移

**结论（2026-09-19 更新）**：归档**本身**仍是查询视图（不新建实体），但因 A4=②（房主可软删归档）需要**一条迁移**：`rooms.archived_hidden_at`。其余（截断、过滤、排序）全部靠现有列。

| 要显示的东西 | 数据来源 | 是否缺 |
| --- | --- | --- |
| 结束时间 / 在房时长 | `rooms.ended_at` / `created_at` | 有 |
| 成员快照与退出原因 | `room_members`（`role / status / exit_reason / joined_at / left_at`） | 有 |
| 申请历史 | `join_requests`（`status / decided_by / decided_at`） | 有 |
| 消息记录 | `chat_messages` | 有 |
| 纪要 | `session_summaries`（M4 建表） | M4 建 |
| 归档软删（A4=②） | **缺** → 需 `rooms.archived_hidden_at`（一条迁移） | 加 |
| 软删后的清理策略（A9=③） | **不做**：M4 不实现清理任务；只把「软删数据不受保护」写成口径，清理留给运维/后续轮次 | 否（口径先行） |

**若要更细（都属 M5 / FQ）**

- 「谁把谁移出」：`room_members` 只有 `exit_reason='kicked'`，没有「执行人」→ 需加 `exit_by` 列（一条迁移）；
- 「个人归档已读 / 收起」：需要按人存视图状态（新表或列）；
- 归档保留期与清理：需要 `hidden_at` / 清理任务。

## 8. 与 M4 纪要设计的接口（含一处修正）

- **修正**：`docs/99-archive/r001-ahead-m4-summaries.md` 写的是「房间详情页可查看纪要」；而**详情页已在 `redirect-06` 删除**。M4 开轮时必须把展示位置改为**归档页 `② 纪要区`**（本页 §5.1），否则又会出现「有数据没入口」。
- 触发链路不变：结束房间 → 自动尝试生成一次（`trigger='auto'`）→ 失败可见 + 可重试。
- 权限对齐：那份设计的 `S-2`（查看权限：与房间详情同级 / 仅房间成员）**建议改为「曾参与即可读」**，与本页 §3 一致。
- 交付证据（M4 需求单里要写的验收）：归档页能看到 `ready` 的纪要正文；「重新生成」走通；`failed` 态可见并重试成功。

## 9. 文案与视觉口径

- 用词：**归档**（名词）/ **查看归档**（动作）/ **结束时间**（不是「关闭时间」）；禁用「回看房间」。
- 气质：归档属于**整理与检索**，沿用列表页的克制工具感（不做交流页的专注感、也不做等待页的温暖感）；消息记录用只读灰阶，纪要按可读排版（`MarkdownLite`），不堆卡片。
- 单点可调（实现时写进令牌）：归档行密度、时间显示格式（相对 `3 天前` / 绝对 `2026-09-19 21:30`）、纪要正文字号。

## 10. 验收点草案（可观察）

1. 结束一间房后：**房主与成员**在 `/archive` 能看到它；**从未参与**的登录用户看不到（查询与页面都没有）。
2. A 页六块齐全（头部 / 纪要 / 成员快照 / 申请历史 / 消息 / 动作），页面内**没有任何写入按钮**（申请、批准、踢人、结束、发消息全无）。
3. 列表页 `ended` 卡片动作 = 「查看归档」，一步进 A 页。
4. 纪要三态可复现：`pending` / `ready` / `failed`（故意用错 Key）+ 重试成功。
5. 边界：未登录访问 `/archive` → 引导登录；直连 A 页 URL 但从未参与 → 403/404 卡片带出口；访问 `active` 房间的归档 URL → `ROOM_ACTIVE` 提示。
6. **迁移与测试**：只有 1 个新迁移（`archived_hidden_at`）；`pytest backend/tests -q` 全绿且含新用例（`was_member` 三态、列表过滤、聚合状态、**截断三态**：从未离开=完整 / 主动离开=截止 / 被移出=截止）。
7. **截断可复现（§3.1）**：`part@example.com` 加入 → 房主再发言若干 → `part` 离开 → 房主结束房间；`part` 打开归档：只看得到他离开前的消息与成员，顶部有「截至你离开时」提示；房主打开同一归档：内容完整。
8. **软删与恢复（A4=② / A9=③）**：房主点「删除归档」→ 二次确认（含「不再受保护、可能被清理、届时无法恢复」）→ 确认后**成员侧归档立刻消失**（列表与直连 A 页都不可见），房主自己仍可见并可「恢复」；恢复成功 → 成员侧重新出现。**失败态**：手工把该房数据注掉后点恢复 → 410 `ARCHIVE_PURGED` + 「该归档已被清理，无法恢复」。
9. **A8=①**：已离开者打开归档 → 纪要区块显示「你离开后生成的纪要不在可见范围」，正文不可读；房主/一直留在房里的成员 → 纪要正文可见。
