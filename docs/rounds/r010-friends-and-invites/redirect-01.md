来源：你 2026-09-19「再加个好友功能，不然邀请对象太泛，同时展示所有在线用户，用一条线分割好友和非好友，记得加被邀请的临时弹窗，邀请人时要能写一句话，有字数限制」。**未批不动代码。**

## 1. 读back

1. **好友功能**：现在只有「限时码」，谁拿到谁都能进 → 太泛。要能**指定人**邀请。
2. **展示所有在线用户**：一个列表把在线的用户都列出来。
3. **一条线分割**：列表里**好友在上、非好友在下**，中间一条分割线。
4. **被邀请时临时弹窗**：对方（被邀请人）收到一个**临时**弹窗，能接受/拒绝。
5. **邀请留言**：邀请时能写一句话，**有字数限制**。

## 2. 与作业必做的关系（重要）

作业必做写死：「**邀请：可生成限时邀请链接或房间码（需设置过期时间）**」。所以：

| 通道 | 是否保留 | 说明 |
| --- | --- | --- |
| **限时邀请码/链接**（r008 正在做） | **必须保留**（作业必做） | 面向「不在好友列表里的人」的通用入口；有效期已按你的口径压到最长 1 分钟 |
| **好友定向邀请**（本轮） | 新增 | 面向好友：选好友 + 一句话 → 对方收到弹窗 → 接受即进房 |

两者并存，互不替代。

## 3. 数据模型草案（待你定后再写函数级设计）

```sql
-- 好友关系（双向一条记录，status 表示是否已互相同意）
CREATE TABLE friendships (
  id TEXT PRIMARY KEY,
  user_a TEXT NOT NULL REFERENCES users(id),   -- 较小的 user_id（保证唯一）
  user_b TEXT NOT NULL REFERENCES users(id),   -- 较大的 user_id
  status TEXT NOT NULL CHECK (status IN ('pending','accepted','blocked')),
  requested_by TEXT NOT NULL REFERENCES users(id),
  created_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
  accepted_at TIMESTAMPTZ
);
CREATE UNIQUE INDEX ux_friendships_pair ON friendships (user_a, user_b);

-- 在线状态（心跳：每次请求/心跳写 last_seen_at；「在线」= 最近 N 秒内有心跳）
-- 方案 A：users 表加 last_seen_at 一列（简单）
-- 方案 B：presence 表（user_id, last_seen_at, room_id）——可顺带显示「在哪个房间」
ALTER TABLE users ADD COLUMN last_seen_at TIMESTAMPTZ;   -- 方案 A

-- 房间邀请（好友定向）：沿用 invites 表，加两列
ALTER TABLE invites ADD COLUMN invitee_id TEXT REFERENCES users(id);  -- NULL = 限时码（任何人可用）
ALTER TABLE invites ADD COLUMN message TEXT NOT NULL DEFAULT '';      -- 邀请留言（已按你要求限字数）
```

## 5. 我看到的两个风险（先说明）

1. **「全站在线」需要心跳**：现在只有登录 Cookie，没有心跳；要么给 `users` 加 `last_seen_at` 并由前端每 30~60 秒打一次（零新依赖），要么引入在线表。心跳本身简单，但会让「在线」有最长 60 秒的误差 —— 你要更准就得上 SSE/WS。
2. **弹窗需要跨用户推送**：站内弹窗必须有通道。我建议先短轮询（8~10 秒），因为项目现在是「HTTP 落库为唯一真相 + DataChannel 只加速」的架构，引入 WS 会和它并列成第二套实时机制，得单独写 ADR。

### 7.1 由「Q7 无时限」引出的两条细则（我按这样设计，你要改说一声）

1. **同一房间 × 同一被邀请人只保留一条有效邀请**：重复邀请＝覆盖留言与时间（`ON CONFLICT`），避免对方弹窗里堆一串。
2. **失效条件**：被接受 / 被拒绝 / 房间已结束 → 邀请不再弹。没有「过期」这一条。

### 7.2 由「Q5 SSE」引出的架构口径

- `GET /api/events`（`text/event-stream`）只推送**通知型事件**：`friend_request` / `friend_accepted` / `room_invite` / `invite_decided`；
- 事件里只带**最小载荷**（谁、哪个房间、邀请 id），前端收到后**照旧走 HTTP 拉真相**（符合「HTTP 落库为唯一真相」，DataChannel 只加速的既有口径）；
- 断线重连：SSE 自带 `Last-Event-ID` 语义，服务端按 `id:` 递增；前端断线时用**短轮询兜底**（30 秒拉一次未处理邀请）——SSE 挂了功能也不丢。
