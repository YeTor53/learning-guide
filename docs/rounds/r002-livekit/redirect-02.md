| # | 缺口 | 现状 |
| --- | --- | --- |
| G1 | **「等候态」不存在**：申请人提交申请后停留在**房间详情页**（按钮 + 状态徽标），没有"等候区"页面；批准后**不会自动进房**，必须自己再点一次「进入房间」；若此时打开 `/rooms/:id/live` 会直接吃到 403 错误卡片 | `r002-livekit-features.md` §F-13「未获批者停留在详情页，看到『等待房主批准』」；§4.3 错误态「未获批」 |

> 判定「等候室有没有设计」取决于口径：按 `docs/glossary.md` 的定义（审批环节）——**有，r001 就做完了**；按「等候室 = 一个能停留、获批即进入的空间」——**没有，G1 就是缺口**。交付要求那句「进入房间前需经过等候室：房主批准后才能进入正式讨论」在两种口径下都满足，差别在体验。

## 4. 需求单口径（一次确认后逐条改）

**A. 建议纳入本轮（G1：等候态）**

- 功能页 F-13 改口径：未获批者打开 `/rooms/:id/live` 时**不再直接报错**，而是进入**等候态**——页面显示「已在等候室：等待房主批准」+ 申请状态（待批 / 已拒绝的说明）+ 「撤回申请」入口 + 「返回房间页」；**每 5 秒轮询** `GET /api/rooms/{id}`，一旦获批**自动连接进房**（无需再点按钮），一旦被拒绝/房间结束则给出对应提示。
- 详情页保留现状（「申请已提交，等待批准」+ 撤回 + 批准后出现「进入房间」），两条路径并存（谁都能用）。
- 无新增后端接口（复用 `GET /api/rooms/{id}` + `POST /api/rooms/{id}/token`）；无新增错误码；只加前端一个状态与一个 `waiting` 分支。
- 验收加一条：**申请人先打开 `/rooms/:id/live` 停在等候态 → 房主批准 → 申请人页面自动进入房间（无需点击）**。
