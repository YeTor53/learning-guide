# redirect r002-05：房间到底是「一次讨论」还是「常设小组」——两种模型对比与建议

## 1. 用户原话 / 问题

> 「这样房间是不是更持久化了，跟初衷相互违背，这种持久化的方案和一次性会议式的方案都想一下，然后对比（但是肯定要改，现在这种肯定不行）」

## 2. 初衷（已批准口径，不是我的揣测）

| 来源 | 原文 | 指向 |
| --- | --- | --- |
| `docs/glossary.md` | 「房间（room）：**一次讨论**的容器，绑定一个主题，有标题与简介，单房间上限 8 人」 | **一次性** |
| `docs/glossary.md` | 「纪要（summary）：房间**结束后**生成的讨论纪要」 | **一次性**（一场讨论 → 一份纪要） |
| `README.md` | 「围绕一门学习主题的多人音视频**小组讨论室**……房间结束后的 LLM 讨论纪要」 | 一次性（有"结束后"这个终态） |
| r001 已实现 | `rooms.status = active/ended`，`ended` 为终态且只读回访；结束时把成员全部置 `inactive/room_ended` | 一次性（散会） |

→ **初衷是会议式**：房间 = 一场讨论，结束即散会（终态），产出纪要。

## 3. 现状为什么会"更像持久化"（真实病灶，共 4 处）

| # | 现象 | 为什么违背初衷 |
| --- | --- | --- |
| P1 | **容量按「在册」计数**（`count_active_members ≥ capacity` 时批准被拒）| ⚠ **本条已于实现期更正**：退场（离开 / 被移出）会把该行置 `inactive`，名额**立即释放**，并非「等房间结束才释放」（实测 `deactivate_member` + `count_active_members`）。真正的问题是它的**名字**叫「成员数」，读起来像长期名册 → 见 P3、P2 |
| P2 | 界面把"成员"当主角（成员总数 2/8、成员列表=名册） | 会议式的主角是"本场出席者"（已改一半：上一轮已按在场分活跃/非活跃，但容量仍是名册口径，所以出现「1/8 在房间，但第 2 人被拒」的矛盾） |
| P3 | 「成员」这个词本身 | 会议式的正确用词是**出席 / 入场**（一次讨论内有效）；"成员"天然读作长期归属性 |
| P4 | 房间不会老化：一个 `active` 房间三个月后仍可进、仍占着 8 人容量 | 一次性讨论应当有"散会"之外的兜底（超时自动结束/归档），否则房间事实上变成常设空间 |

## 4. 两种模型对比

### 模型 A：一次性讨论（会议式）——与初衷一致

| 维度 | 规则 |
| --- | --- |
| 房间 | 一场讨论；`active → ended`，`ended` 为终态、只读回访（看纪要/出席快照） |
| 容量 | **座位口径**：在场人数 < capacity 且「已批准未入场」也占座 → 两者之和 < capacity 才可入；人退场即释放座位 |
| 角色 | 房主 = 创建者（本场主持人）；协管 = 本场临时授权，散会作废（历史保留） |
| 出席 | 批准 = 拿到本场入场资格；离开/被踢 = 本场退场（可重新申请入场）；**不跨场沿用** |
| 结束 | 散会：删 LiveKit 房 + 全员退场 + 生成纪要（M4）；不可重开（要再讨论 = 新建房间） |
| 持久物 | 房间基本信息 + 主题 + 房间码 + 申请记录（审计）+ 出席快照 + 纪要 |
| 变更量 | **schema 不动**（`room_members` 语义重定义为"本场出席记录"）；服务层改 1 处规则（容量口径）；术语与文案改 3~4 处；验收改 2 条 |

### 模型 B：常设小组（持久化）

| 维度 | 规则 |
| --- | --- |
| 房间 | 一个学习小组的空间；成员是**组员**（长期） |
| 讨论 | 需要新概念 **session（场次）**：小组下可开多次，每次有开始/结束/纪要 |
| 容量 | **组员上限**（例如 8 人小组），与在场无关 |
| 角色 | 组员角色长期有效（可增删组员） |
| 结束 | 「结束本次讨论」≠「解散小组」；小组可归档 |
| 变更量 | **schema 改**（新增 `sessions`，`rooms` 拆成 group+session 语义，`room_members` 变 `group_members`，`join_requests` 要挂到场次还是小组需重新设计）；r001 已实现的 9 条接口与验收大部分要重写；M2 的踢人/角色/容量/结束语义全部要重新对齐；演示脚本重写。**本轮等于推倒重来** |
| 与初衷 | 违背术语表「房间=一次讨论的容器」；纪要也失去"一次讨论"的锚点 |

### 模型 C：现状（混合体）

持久成员名册 + 一次性房间终态 → **两套语义互相打架**：容量不释放（A 的话术、B 的规则）、界面讲在场而规则讲名册、`ended` 回访是"讨论记录"却挂着"成员名册"。

## 5. 建议

**选 A（一次性讨论 / 会议式）**，理由：
1. 与术语表、README、r001 已批准并已实现的终态语义一致；选 B 要改已批准的 r001 契约（L3）且本轮推倒重来；
2. 交付要求（面试作业）看的是"能不能把一场讨论办完并留痕"（等候室 → 讨论 → 权限 → 纪要），不是"能不能运营一个社群"；
3. A 的病灶只有 P1~P4 四处，**schema 零改动**，可在 cp-r002-4 之前收口；B 的病灶是模型级。

**A 下要改的四处（本轮内）**

| # | 改动 | 落点 |
| --- | --- | --- |
| A-1 | 容量口径：`在场人数 + 已批准未入场人数 < capacity` 才允许入；批准时与取票时**都**校验（保留 r001「满员时批准被拒」，并补"取票时也拦第 9 人"） | `services/rooms.py`（`approve_join_request` + `issue_room_token`）、`services/livekit.py` 不动；用例 +2 |
| A-2 | 术语与文案：「成员」→「出席 / 入场」口径（术语表加「出席记录」；抽屉/管理页文案统一为"在场 / 已退场"） | 术语表、功能页、前端文案 |
| A-3 | 角色有效期写明：**本场有效**（散会作废，历史保留） | ADR-0012、功能页角色矩阵脚注 |
| A-4 | 「房间不老化」登记 backlog（超时自动散会/归档，M5 定时校准一起做） | roadmap §9.1 |

**A 下不变的东西**（明确写清，避免你以为都要改）：`rooms`/`room_members`/`join_requests` 表结构与已实现接口全部保留；被踢者可再申请（FQ-3）保留；`ended` 只读回访保留（它就是纪要/出席快照的载体）；**要再讨论一次 = 新建房间**（M3 可加「复制房间再开一次」的便捷入口，不进本轮）。

## 6. 待你拍板的 4 条（都不改就是按建议值）

| 编号 | 事项 | 建议值 |
| --- | --- | --- |
| Q-A1 | 容量口径 | **座位口径**：在场 + 已批准未入场 < capacity |
| Q-A2 | 批准时是否仍校验容量 | **是**（保留 r001 行为），取票时再兜一次 |

## 6.5 等候与入场口径（用户 2026-09-18 修订，详见 ADR-0012 修订节）

> 用户原话：「不要未入场，申请之后进等待室，申请允许后直接进入，失败回到主界面，不要有手动加入这一步。」

| 场景 | 修订后的处理 |
| --- | --- |
| 容量怎么算 | **按在场人数**（LiveKit 实测），不再按在册；**没有「未入场占座」这个概念** |
| 满员时能否申请 | **能**（申请不校验容量）→ 申请人进等待室，可撤回 |
| 房主批准 | **不校验容量**（批准 = 授予入场资格）；房主侧显示「在场 N / capacity」自行判断 |
| 申请人怎么进房 | 等待页轮询到「已批准」→ **自动取票 + 自动连接**，**无需手动点进入** |
| 满员导致进不去 | 取票时 `ROOM_FULL` → 等待页显示原因 → **自动回主界面（房间列表）** |
| 手动「加入」步骤 | **取消**；管理页对在册成员保留的是「回到讨论」（重进，不是加入） |
| 自动放行（FIFO） | 仍**不做**（M5 backlog）；房主逐个批准 |

## 7. 结论

- 定性：**A（一次性讨论）已批准**；实现期核实：**容量规则无需改动**（现状已是在册占座 + 退场即释放），实际要改的是**口径与文案**、**等待页第二态**与**满员提示**，外加 2 条新用例。schema 与 r001 接口零改动。
- 批准后我按顺序落：ADR-0012（房间生命周期：一次性讨论）→ 需求单/功能页/实现页口径对齐 → A-1 代码与用例 → 术语表与文案 → roadmap 台账。
- 若你要选 **B（常设小组）**：请明确说，我会另出一份"B 的完整改造清单与工作量估算"，但在本轮内不启动（它要重排 M2 的全部验收）。
