# redirect r002-06：房间管理页是否移除？——建议「不删，降型为门口页」

## 1. 你的问题

> 「思考管理页是否该移除，太『重型』了」

## 2. 现状盘点：这一页现在装了什么

`/rooms/:id`（`RoomDetailPage.tsx`）目前在一屏里混装五件事：

| 内容 | 是否有别处可做 |
| --- | --- |
| 房间信息（标题 / 主题 / 简介 / 房间码 / 创建时间 / 上限） | 房内抽屉有房间码（其余没有） |
| 成员名册（含非活跃、退出原因） | **房内抽屉有**（按活跃/非活跃分组） |
| 申请处理（全量历史 + 留言全文 + 批准/拒绝） | **房内抽屉有**（只 `pending`） |
| 进房 / 离开 / 结束房间 | 进房从列表页也有；离开/结束在房内也有 |
| 只读回访（`ended` 后的历史） | **没有** |

→ 五项里 **三项与房内抽屉重叠**，这正是"重型"的来源；但**「只读回访」和「未在册者的落脚点」两项是它独有的、且删不掉的功能**。

## 3. 四个选项

| 选项 | 做法 | 代价 | 判断 |
| --- | --- | --- | --- |
| A 完全移除 | 只留交流页 + 抽屉；`ended` 后无回访页 | ① 分享链接没有落点（访客直接吃"你不在房间里"→等待室）；② 未在册者看不到房间是什么就得先申请；③ 纪要（M4）没有载体；④ 删已验收页面（L3） | ✗ 不建议 |
| B 保留但降型为「**门口页**」 | 去掉成员治理动作与申请处理（只在房内抽屉做）；保留房间介绍 + 入口按钮 + 只读回访 | 改 1 页 + 动 r001 验收口径（L3） | ✓ **建议** |
| C 拆成两页 | 「房间说明页」+「历史/纪要页」 | 页面数不减反增，与"降重"目标相反 | ✗ |
| D 反向合并（砍抽屉，全走管理页） | 一切治理回管理页 | 违背 ADR-0012/D7：跳页 = 断开讨论，"为了批准一个人先退出讨论" | ✗ 已否 |

## 4. 建议：保留页面，把它从「管理台」重新定名为「门口」

- **页面身份**：`/rooms/:id` = **房间门口（room landing）**：看这是不是我要进的房间 → 申请 → 等 → 自动进去；进来过的人从这里「回到讨论」。
- **留在门口页**：房间介绍（标题 / 主题 / 简介 / 房主 / 上限 / 房间码 / 当前在房间人数）、**入口按钮**（在册 →「回到讨论」；待批 →「去等待室」；未在册 →「申请加入」→ 直接进等待室）、房主的**危险动作「结束房间」**（二次确认）、`ended` 后的**只读回访**（房间信息 + 申请历史 + 成员快照）。
- **移出门口页**：成员治理（移出 / 设为协管 / 取消 / 移交房主）与申请批准/拒绝 → **只在房内抽屉**。理由：治理发生在讨论中；不在房里时没有"边看边管"的场景。
- **房主不在房里但门口有人等** → 门口页只给一句引导：「门口有 N 位在等 → 进房处理」，把他送进交流页（不在这页重复提供批准动作，两页职责不再重叠）。
- **列表页**：卡片进门口页；在册房间的卡片**直接给「回到讨论」按钮**（少一次跳转）。

## 5. 影响与成本

| 面 | 影响 |
| --- | --- |
| 后端 | **0 改动**（所有接口都已存在，只是调用点变化） |
| 前端 | `RoomDetailPage.tsx`：删成员治理/申请处理区块与相应 mutation；改页面身份文案（「房间管理」→「房间门口」/「房间介绍」）；加"进房处理"引导；`JoinRequestList` 在该页不再使用（房内抽屉继续用） |
| 文档 | 功能页 F-02/F-03、§4.9 分工表、按钮矩阵、需求单验收（r001 E1~E10 中"在管理页批准/拒绝"的表述改为"在房内抽屉"）→ 属 **L3（动已验收口径）** |
| 验收 | 演示脚本把治理步骤全部落在房内抽屉；门口页只验"看信息 → 申请 → 等待室 → 自动进入"与 `ended` 回访 |
| 术语 | 术语表「房间管理页」→ 改为「房间门口页（room landing）」，并注明"治理动作在房内抽屉" |

## 5.5 必要性复核（你追问「门口页存在的必要性是什么」后，我改主意了）

逐条压力测试我上一版给出的三条「必要性」，**两条不成立**：

| 我原来的理由 | 复核 | 判定 |
| --- | --- | --- |
| ①「分享链接需要落点」 | 房间列表页本来就把所有 `active` 房间连同标题、主题、成员数一起列出来，卡片上就有「申请加入」；房间码也能口头给。**深链分享**（把某个房间的 URL 发给别人）确实需要落点，但交付要求从未要求邀请/分享链接（`invites` 已拆 backlog） | **弱**（nice-to-have） |
| ②「未在册者要先看清房间再申请」 | 两条更轻的载体已经够：列表页卡片（标题/主题/人数）+ **等待室**（已显示标题、主题、房主、上限、简介）。申请前的「了解」不需要再单独一页 | **不成立** |
| ③「`ended` 后只读回访（历史 + M4 纪要载体）」 | 唯一真实需求，且**它不需要「管理页」也不需要「门口页」**：回访/纪要天然是一条独立的路，路由可以继续叫 `/rooms/:id`，M4 也可以自己开 `summary` | **成立，但与治理是两件事** |

**结论修正**：`/rooms/:id` 的真实必要性只有两条——**深链落点** 与 **`ended` 回访**；我上一版把它重新包装成「门口页」是**过度设计**（为了保住一页而给它编了一个身份）。

## 5.6 修正后的建议：不叫「门口页」，而是把 `/rooms/:id` 降级为「房间信息 + 回访页」

| 场景 | 由谁承载 |
| --- | --- |
| 发现房间 | **列表页**（已有筛选与卡片） |
| 申请 → 等待 → 自动进入 | 列表页卡片「申请加入」→ **等待室** → 交流页 |
| 讨论中的治理（批准/移出/授权/移交） | **房内抽屉**（ADR-0012 判据：跳页 = 断开讨论） |
| 结束后的回访（历史；M4 起含纪要） | **`/rooms/:id`（只读回访页）** |
| 深链分享（可选） | 同一个 `/rooms/:id` |

`/rooms/:id` 降级后**只有**：房间信息（标题/主题/简介/房主/上限/房间码/创建时间/状态）、`ended` 时的历史（申请记录 + 成员快照）、**一个主按钮**（在册 →「回到讨论」；未在册 →「申请加入」→ 等待室；待批 →「去等待室」）。**没有**成员治理、**没有**申请处理、**没有**离开/结束（结束留给房内抽屉；若你要页内也能结束，见 Q-B3）。

列表页入口随之改：在册房间的卡片**直接给「回到讨论」**（不再先绕 `/rooms/:id`）；`ended` 房间的卡片给「查看回访」。
