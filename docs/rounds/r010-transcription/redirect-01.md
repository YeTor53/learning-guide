## 1. 读back

1. **默认开启**：一进房间就在转写（可关），不需要本人先去点开关。
2. **说的话并入「文字对话」**：语音转出来的文字出现在房间讨论记录里，与群聊/系统消息是同一条流，不再是单独的「转写片段」列表。
3. **还要包含成员进出等管理信息**：房间事件系统消息（加入/离开/被移出/成为房主/房间已结束/满员未通过，r005 已有）与语音文本同流，构成**完整会议记录**：`聊天 + 系统消息 + 语音文本`。
4. **STT 获取方案要单独设计**：先讲清「用哪家、怎么拿、成本与限额、云/自建、离线兜底」，再动手。

## 2. 三个真难点

| 难点 | 说明 |
| --- | --- |
| 数据模型 | 讨论记录目前混着 `chat_messages`（含 `kind='system'`）。语音文本进来要定：**同表加 `kind='speech'`** 还是**独立 `transcripts` 表 + 查询合并**；合并后排序键、分页、「加载更早的消息」、房间结束后的只读视图都要跟着改 |
| 默认开启的隐私 | 默认开启 = 每个进房的人默认被转写 → 需要：进房一次性明确告知、一键关闭、关闭后立刻停传、文本可见范围约定 |
| 实时性与成本 | 15 秒一段太慢；要「边说话边出字」得 3~8 秒分段或流式 STT，成本与复杂度上一个台阶，要定「够用就好」的档位 |

## 3. STT 获取方案（本轮要先产出的**设计**）

| 方案 | 怎么拿 | 优点 | 代价 |
| --- | --- | --- | --- |
| A. 云端 OpenAI 兼容 Whisper（OpenAI / 硅基流动 / 百炼 / 火山等） | 申请 API Key，`POST /audio/transcriptions` | 接入最快（`STT_*` 三键已预留）、中文稳定 | 按量计费、有并发与时长限额、需联网 |
| B. 本地 faster-whisper / whisper.cpp | 本机或服务端跑模型 | 零调用成本、数据不出本机 | 吃 CPU/GPU、要装环境、部署复杂 |
| C. LiveKit 侧转写（Agents / Egress + STT 插件） | 走 LiveKit 云能力 | 服务端拿音轨、不依赖前端上传 | 额外服务与配置、成本更高 |
| D. 浏览器 Web Speech API | 前端直接用 | 零后端成本、亚秒级 | 中文质量参差、浏览器支持有限、不可复现 |

> 产出要求：选 1 主 + 1 兜底，写清「怎么申请 / 键名与 `.env` / 限额与成本估算 / 失败降级（未配置 → 功能禁用并提示）/ 隐私说明」。
