本页是 r002（M2）的**功能页**：使用者看到什么、能点什么、点了之后看到什么。
实现（数据、接口、函数路径）以 **实现页** `docs/02-modules/r002-livekit.md` 为准；本轮范围与验收见需求单 `docs/00-requirements/r002-livekit-room.md`；
r001 已有功能（浏览/建房/详情/申请/批准/拒绝/撤回/离开/结束/只读回访）见 `docs/02-modules/r001-rooms-features.md`，本页只写增量。
**页面口径（`redirect-04` 三分 → `redirect-06` 两页 + 列表）**：**列表页**（`/`，发现与申请入口）→ **交流页**（`/rooms/:id/live`，专注感）→ **等待页**（`/rooms/:id/wait`，温暖感）；原「房间管理页 `rooms/:id`」**已删除**（治理动作全部在交流页的「成员与管理」抽屉里，理由：跳页 = 断开讨论；见文末 §4.9 与 `docs/rounds/r002-livekit/redirect-06.md`）。

## 1. 使用者与角色

| 角色 | 怎么产生 | 房内可见范围 | 房内可做 |
| --- | --- | --- | --- |
| Host（房主） | 建房者；或被上一任 Host「移交房主」 | 全部 | 处理申请、踢任何人（除自己）、任命/取消协管、移交房主、结束房间 |
| Moderator（协管） | 被 Host「设为协管」 | 全部 | 处理申请、踢参与者（**不能**踢协管、不能踢 Host、不能踢自己） |
| Participant（参与者） | 申请获批 | 全部 | 开关自己的麦克风/摄像头、离开房间 |
| 已结束房间的任何人 | —— | 只读（成员、消息、纪要） | 无房内操作；「进入房间」按钮消失 |

## 3. 功能详述

### F-13 进入房间

- **入口**：列表页卡片「回到讨论」（仅当「我是该房间的**活跃成员**」且房间 `active` 时出现）；等待页获批后自动进入；建房成功直接进入。
- **另一条入口**：等待页获批后自动进入（`--wait-autoenter-delay`，默认 1.5 秒；可在等待页关闭自动进入）。
- **未获批者**：列表页卡片给「申请加入」（提交后直接落等待室）；若直接打开 `/rooms/:id/live` → **被送到等待页**。
- **容量闸在取票**（ADR-0012 修订 D5）：`在场 >= capacity` → 409 `ROOM_FULL`；外部查询失败降级放行，由 Token `max_participants` 兜底。**申请与批准都不校验容量**（D2/D3）。
- **行为**：进入交流页后自动取 Token 并连接（**不做 prejoin 弹窗**）→ 连接成功后看到舞台与自己的画面。
- **首次授权**：浏览器会弹「允许使用麦克风/摄像头」；拒绝或没有设备时，进房成功但自己的格子显示姓名首字头像块，页面顶部提示「未获得摄像头/麦克风权限，其他人听不到你说话」。
- **提示**：实时服务不可用 → 页面内错误卡片「实时服务暂时不可用，请稍后重试」+ 重试；房间已结束 → 「房间已结束，仅可查看历史内容」+ 返回详情。
- **验收点**：两个浏览器用**不同账号**进同一房间，能互相听到、看到；刷新页面自动重连。

### F-14 实时在场与本地设备控制

- **视频格**：参与者按人数自适应（1 人铺满 → 2 人并排 → 3 人以上网格）；格子显示画面、姓名、角色徽标、静音徽标；无摄像头时显示姓名首字头像块。
- **成员侧栏**：以**库成员列表**为骨架，LiveKit 在场者标「在线」，其余标「离线」（灰显，承接实现页 R-7 的建议值：显示离线成员，房主才能看到谁掉了）。
- **设备控制条**：麦克风开关、摄像头开关、「离开房间」；状态用图标 + 文字（不用颜色单独承载信息）。
- **连接状态徽标**（顶栏房间条）：已连接 / 正在重连… / 已断开；重连中不弹窗、不退出房内页。
- **设备状态保持**：麦克风/摄像头的开关在重连前后保持一致（关着的回来还是关着）。
- **规则**：静音/关摄像头只影响自己，不广播弹窗；他人格子上的对应徽标实时变化。
- **验收点**：A 关摄像头 → B 侧格子立即变为头像块；A 静音 → B 侧出现静音徽标。

### F-10 踢出成员

- **入口**：房内页成员行内「移出房间」（Host/Moderator）。
- **限制**：不能踢房主；协管不能踢协管（仅房主可）；不能踢自己（自己用「离开房间」）。
- **行为**：二次确认弹窗（「将 X 移出房间？对方会立即断开连接」）→ 确认后该成员：成员列表标记「被移出」；对方连接被**服务端强制断开**并显示「你已被移出房间」（非前端假踢）；被移出者可再次提交申请（承接 r001 FQ-3：立即允许）。
- **提示**：权限不足 → 「没有权限执行该操作」；实时服务调用失败 → 「已移出 X，但实时断开可能延迟」。
- **验收点**：踢人后对方页面**立刻**跳到「你已被移出房间」；刷新页面也回不来（Cloud 下旧 Token 已失效）；库内该成员 `status='inactive'`、`exit_reason='kicked'`。

### F-11 任命协管 / 移交房主

- **任命协管**：Host 在成员行选「设为协管 / 取消协管」；协管随即获得处理申请、踢人（除协管互踢）、（后续 M3 的）举手管理等能力；角色变化**立即**反映在双方页面的按钮可见性上。
- **移交房主**：Host 选「移交房主」→ 二次确认（「移交后你将变为协管，且不能再收回」）→ 双方角色互换：对方成为 Host，你变为**对方原来的角色**（参与者或协管）。
- **提示**：非 Host 看不到这两项（前端隐藏 + 服务端 403 双保险）。
- **验收点**：任命后对方能踢人、能批申请；移交后原 Host 的列表项变为「协管」，且其按钮集同步收窄。

### F-15 离开 / 被移出 / 房间结束的断开表现

| 来源 | 使用者看到 | 库内结果 |
| --- | --- | --- |
| 主动「离开房间」 | 回到房间详情页，提示「已离开房间」 | 成员 `inactive/self_leave` |
| 被 Host/协管移出 | 页面内卡片「你已被移出房间」+ 「返回房间列表」 | 成员 `inactive/kicked` |
| Host 结束房间 | 所有端卡片「房间已结束」+ 「查看讨论记录」 | 房间 `ended`；成员 `inactive/room_ended` |
| **重连中**（网络抖动/短时断网） | 徽标转「正在重连…」，画面可能短暂卡住但**不退出房内页**；其他端看到你短暂「离线」再回在线 | 无变化（重连不改库） |
| **重连成功** | 徽标回「已连接」，声画恢复，麦克风/摄像头保持原来的开关状态 | 无变化 |
| **同账号在第二个窗口进入同一房间** | 先进入的那个窗口被断开并提示「同一账号已在别处进入本房间」 | 无变化（两条连接不是两条成员记录） |
| 网络断开且重连失败 / 关标签页 | 「连接已断开」+ 重连按钮；**库内不变**（仍算成员，侧栏显示离线） | 无变化（判定留 M5） |
| 登录过期 | 「登录已失效，请重新登录」+ 去登录（带 `returnTo`） | 无变化 |

### F-16 交流页（专注感）

- **进入方式**：① 等待页获批后**自动进入**（不点按钮，ADR-0012 修订 D4）；② 在册成员从管理页「**回到讨论**」重进（D7，重进而非「加入」）。
- **界面只有三块**（其余一律不做）：
  1. **顶部 44px 细状态条**：左侧「← 房间管理」（带断开确认）· 房间标题 · 在房间人数「N / 8 在房间」· 房间码 · 在房时长；右侧连接状态徽标 + **带文字的「成员与管理」按钮**（有未处理申请时：强调色填充 + 数量徽标 + 一次脉冲）。管理动作全部收进抽屉（默认收起），分工见 §4.9。
     - **待处理申请的两级提示**（你 2026-09-18 提「成员与管理员不明显、音视频内的管理看不到申请、新申请没通知」）：① 按钮徽标（`N`）+ 强调色填充；② 抽屉关着时状态条下方出现一行 `门口有 N 位在等房主批准 [去处理]`，点击直接打开抽屉；③ 新申请到达时按钮脉冲一次（2.4 秒，`prefers-reduced-motion` 下不动）；④ 抽屉内区块标题显示 `待处理申请 · N`。**不弹窗、不 toast**（redirect-03 未批前不预判）。
  2. **舞台**：单焦点布局——说话者/共享者占主格，其余人为窄缩格；非焦点格降饱和 35%、亮度 −12%，焦点格上缘 2px 强调线；无摄像头者显示姓名首字头像块。
  3. **底部控制坞（`DeviceBar`）**——**分组 + 状态文字 + 电平 + 防呆**，不是三个等形圆按钮：
     - **左组·设备**：`[麦克风 + 电平条]` `[摄像头 + 已开/已关]`。开麦时显示三段电平条（≈12fps 采样 `localParticipant.audioLevel`，平滑下落），关麦时文字显示「已静音」；关闭态用**危险色 + 文字双重表达**（颜色不可靠、文字才可靠）。tooltip 带快捷键：麦克风 `M`、摄像头 `V`。
     - **分隔线**：设备组与离场组之间一条竖线，物理隔开「常按」与「不可逆」。
     - **右组·离场（按角色分岔，r003）**：**房主**看到的是 `结束房间`（危险色描边 + 危险色 hover，`--live-end-border` / `--live-end-hover` 单点可调），点击后在坞内就地展开确认「结束这个房间？所有人将被移出、需重新申请才能进；房间转为只读，历史仍可查。」+ 结束房间 / 取消（`Esc` 取消）；**协管与成员**看到的是 `离开`，确认文案「离开后要重新申请才能进来，确定吗？」。两组都**用描边而非填充**（不抢主视觉）、**不绑定任何快捷键**（离场与结束都必须是有意的）。
     - M3 的屏幕共享 / 举手 / 焦点 / 聊天**预留位置但不出现按钮**。
  - **防呆清单（F-16 的硬要求）**：① 离开必须二次确认且不绑快捷键；② `Esc` 永远有退路（先取消确认、再收抽屉）；③ 重连中（`connecting` / `reconnecting`）禁用全部按钮，避免「点了没反应」；④ 房主没有「离开」按钮：他的离场位**就是**「结束房间」（危险色），仍要二次确认才生效；若走其他路径触发离开，前端与服务端仍拦（`HOST_CANNOT_LEAVE`，提示「请先移交房主或结束房间」）；⑤ 关麦/关摄像头是**文字 + 颜色**双提示，不靠颜色单通道；⑥ 输入框聚焦时快捷键不生效（避免打字时误切麦）。
- **专注模式（界面会退场）**：静默 30 秒后顶部条与底部控制条淡至 45% 不透明度；指针移动、键盘聚焦、任何人说话时立即恢复（参数 `--live-chrome-idle-seconds` / `--live-chrome-idle-opacity`）。
- **零装饰**：不加载首页的 Canvas 流场、网格质感层与《思想者》图版（ADR-0008 的装饰清单在交流页显式不适用）。
- **反馈不抢注意力**：成功类反馈只用状态条微亮；**只有失败才弹 toast**（`redirect-03` 口径）。
- **降级**：`prefers-reduced-motion` 下取消位移与呼吸，只保留不透明度变化。
- **验收点**：两人以上进房 → 说话者格自动放大且其余格降权（肉眼可见）；鼠标静止 30 秒 UI 淡出、动一下立刻回来；页面里找不到任何装饰元素。

### F-17 等待页（温暖感）

- **进入方式**：列表页卡片「申请加入」（提交后直接落到这里）或「去等待室」（有待批申请时）；**有 `pending` 申请**者直接打开 `/rooms/:id/live` 也被送到这里。**被移出 / 已离开的人不会被送到等待页**——他们没有待批申请，交流页取票 403 时回**房间列表页**并提示「你已被移出房间，可以重新申请加入」。
- **界面内容**（自上而下）：
  1. 暖色呼吸光（左上径向，6 秒周期、幅度 4%）+ 一句话安抚文案；
  2. **三步状态时间线**：已提交 → 等待房主批准 → 进入房间（当前步暖色微亮，后续步灰）；
  3. 房间卡：主题、标题、房主显示名、人数 `N / 8`；
  4. 主题简介（把等待变成期待：先看一眼今天要聊什么）；
  5. 次级操作：「撤回申请」「回房间页」常驻可点。
- **两态等待**：① **等房主批准**（`pending`）——呼吸光 + 时间线；② **等待入场**（已批准、正在取票/连接）——文案「房主同意了，正在把你送进去」。
- **获批行为**：5 秒轮询发现已批准 → **自动取票 + 自动连接**（无手动步骤）→ 进入交流页。
- **失败回主界面**（D6）：`ROOM_FULL` / `ROOM_ENDED` / 网络失败 → 原地显示服务端原因 3 秒 → **自动回房间列表页**；被拒 / 已结束时中性提示「重新申请」或「回列表」。
- **语气示例**（短句、第一人称、不卖萌、零 emoji）：「你已经在门口了，房主看到就会开门」「房主通常很快处理」「等待的时候可以先看一眼今天的讨论主题」。
- **验收点**：呼吸光可见且 6 秒一循环；时间线当前步高亮；撤回后按钮变「再次申请」；获批后 1.5 秒自动进入交流页；reduced-motion 下呼吸静止。

## 4. 页面级交互设计

### 4.1 交流页（`/rooms/:id/live`）布局 —— 专注感

```
┌ 44px 细状态条：房间标题 · 人数 N/8 · 连接状态徽标 · 房间码 ── [管理抽屉开关] ┐
│                                                                          │
│                  舞台（单焦点：说话者/共享者主格 + 其余窄缩格）            │
│        非焦点格降饱和 35% / 亮度 −12%；焦点格上缘 2px 强调线              │
│                                                                          │
│            〔管理抽屉（默认收起）：成员 · 待批申请 · 管理动作〕             │
│                                                                          │
│         （底部悬浮控制条，居中）麦克风 · 摄像头 · 离开房间                  │
└──────────────────────────────────────────────────────────────────────────┘
   静默 30 秒 → 状态条与控制条淡至 45%；指针移动 / 键盘聚焦 / 有人说话 → 立即恢复
```

- **零装饰**：不加载首页的 Canvas 流场、网格质感层与《思想者》图版（ADR-0008 的装饰清单在交流页显式不适用）。
- 视觉沿用暗色编辑风与令牌（`docs/04-style/global-style.md`）；图标一律 Lucide，界面零 emoji；底色比列表页更暗一档（专注感）。
- 空态：只有自己时，舞台中央「等待其他人加入」（低对比、无插画）。
- 错误态：不显示黑屏——先渲染错误卡片与原因文案；**「未获批」不再是错误态**，而是被送到等待页（§4.4）。

### 4.2 按钮矩阵（交流页 · 管理页 · 等待页）

| 位置 | 按钮 | Host | Moderator | Participant | 条件 |
| --- | --- | --- | --- | --- | --- |
| 管理页 | 进入房间 | ✅ | ✅ | ✅ | 我是活跃成员且房间 `active` |
| 管理页 | 去等待页 | ✅ | ✅ | ✅ | 我已提交申请且仍在 `pending` |
| 等待页 | 撤回申请 / 回房间页 | ✅ | ✅ | ✅ | 恒显示 |
| 等待页 | 取消「自动进入」 | ✅ | ✅ | ✅ | 获批后 1.5 秒内 |

### 4.7 专注感的四个来源（交流页，用户追问「专注感呢」后定稿）

「把底色调黑」本身不产生专注感——第一版实测就是一块空黑 + 一个巨字，读起来是"空"，不是"专注"。专注感由四件事共同产生：

| 来源 | 做法 | 参数（单点可调） |
| --- | --- | --- |
| ① 收拢的注意力 | 舞台四角暗角 + 顶部一线主题色光带（不是装饰图形，是光）；焦点格上缘 2px 强调线 + 内发光；非焦点格降饱和/降亮并**沿右侧竖排**（退到边上，而不是与主格并排抢眼） | `--live-vignette`、`--live-tint`、`--live-focus-glow`、`--live-focus-dim`、`--live-rail-width` |
| ② 可见的现场 | 无摄像头时不是灰字占位，而是主题色渐变头像圆块；**说话时三圈渐隐声波脉冲**（`reduced-motion` 下改为静态光环） | `.live-avatar`、`.live-avatar-pulse`（1.8s 循环） |
| ③ 启动的边界感 | 进房瞬间顶部出现欢迎胶囊「已进入 · 主题 · 上限 N 人」，3.2 秒后自动淡出，把"现在开始专注"这件事标出来 | `@keyframes live-welcome`（3.2s） |
| ④ 正向的节律 | 状态条右侧一个安静的**在房时长**（`00:12`，tabular-nums，灰色小字，不做倒计时），给"我们一起专注了多久"的反馈；静默 30 秒后随界面一起退场 | `.live-focus-timer`、`--live-chrome-idle-*` |

反向要求（同样重要）：不加背景动画、不加装饰图层、不加渐变动态、不弹成功提示——**专注感的敌人是"更多东西"，不是"更少的黑"**。

### 4.9 治理为什么只在交流页的抽屉里（`redirect-06` 定稿：删除房间管理页）

用户 2026-09-18 先问「成员与管理和管理页是不是有点冲突」，再问「管理页是否太重型」，最后定：「删了吧」。结论：**原房间管理页（`/rooms/:id`）删除**，治理动作只在交流页抽屉。分工依据只有一条：

> **在交流页里点一下就能做完的事，不该要求用户跳到管理页去做。** 交流页跳转 = 组件卸载 = LiveKit 断开，"为了批准一个人而退出讨论"是本末倒置。

| 维度 | ~~房间管理页（`/rooms/:id`，已删除）~~ | 交流页的「成员与管理」抽屉 |
| --- | --- | --- |
| 定位 | **完整治理**：可停留、可分享、可刷新、可只读回访 | **房内即时手术**：讨论进行中，快速处理"门口有人等 / 有人捣乱" |
| 申请处理 | 全量历史（批准 / 拒绝 / 已撤回 / 已取消 / 已拒绝）+ 留言全文 | **只有 `pending`**（`pendingOnly`），做完即消失 |
| 成员 | 全部成员卡片（含加入时间、退出原因历史、非活跃灰显） | 按**在不在房间内**分两组：活跃（在房间里）/ 非活跃（不在房间内，注明离线或退出原因）+ 角色 + 即时动作 |
| 房间信息 | 主题、简介、房间码、创建/结束时间 | **不放**（与管理页重复）；只留一行「房间码 + 复制」，因为讨论中要口头传播 |
| 动作 | ~~申请 / 离开 / 结束 / 进入房间~~（页面已删） | 批准、拒绝、移出、设为协管 / 取消、移交房主；**房主的「结束房间」在控制坞离场位**（r003 定：不重复放进抽屉） |

**判定规则（以后加功能照此办）**：出现「同一份信息两处维护」时，**留在管理页**；只有「讨论中真的会用到的动作或数字」才进抽屉。据此本轮删掉了抽屉里的主题/简介段（与管理页重复）。

### 4.8 屏幕共享：可行性与布局预留（本轮**不做**，为 M3 铺路）

用户 2026-09-18 要求「思考屏幕共享的可能」。结论：**本轮只做布局预留，不出现任何共享按钮**；M3 落地时不需要改 Token 口径。

| 维度 | 结论 |
| --- | --- |
| 技术可行性 | LiveKit 原生支持：客户端 `localParticipant.setScreenShareEnabled(true)`；事件 `TrackPublished(source = ScreenShare)`；我们的 Token 用 `canPublish=true`（未限源）→ **已允许发布共享轨**，无需改 `services/livekit.py` |
| 焦点优先级 | **屏幕共享 > 说话者 > 自己**——本轮已在 `LiveStage` 里实现（`useTracks` 同时订阅 `ScreenShare` 与 `Camera`），M3 落地时不改布局代码 |
| 比例与限幅 | 共享内容以 16:9 为主，焦点格已按 `--live-focus-ratio` 做 letterbox（`object-fit: contain`）并有高度上限 → 共享画面不会被拉伸或撑爆 |
| 谁可以停 | 建议 M3 做「Host/协管可停止他人共享」：需 `UpdateParticipant` 或把 `canPublishSources` 收窄为摄像/麦克风；属 M3 的服务端轨道权限，本轮不做 |
| 防呆（M3 实现时的硬要求） | ① 共享必须由用户手势触发（浏览器 `getDisplayMedia` 强制），不做"进房自动共享"；② 共享中焦点格给「正在共享 · 名称」徽标 + 显眼的「停止共享」入口；③ 共享音频需用户显式勾选（浏览器限制），界面如实说明；④ 自己的共享也进焦点格，但要标「这是你的共享」避免混乱；⑤ `prefers-reduced-motion` 下不加共享动画 |
| 风险与不做理由 | 演示场景下误共享私人窗口代价高、浏览器差异大（Safari/Firefox）、且 M2 验收点未含共享；故放 M3，与聊天/举手/焦点发言一起做 |
| 成本估算（M3） | 前端 +1 hook（`useScreenShare`）+1 按钮（控制坞左组第三颗）+ 焦点格徽标；后端 0；演示脚本 +1 步 |

### 4.6 按钮设计决策表（r002 定稿，覆盖交流页与管理页）

判定轴同控制坞：**功能是否必要 → 放哪 → 怎么展示 → 怎么提示 → 怎么防呆**。结论三态：保留 / 改 / 不做。

## 6. 端到端演示脚本（两个浏览器，人工）

准备：浏览器 A（`host@example.com`）、浏览器 B（`part@example.com`）；后端 dev 形态在 8000、前端在 `localhost:5173`（`localhost` 而非 `127.0.0.1`——浏览器只在安全上下文允许采麦克风/摄像头）。

1. A 建一间房（容量 3，便于演示满员），把房间码给 B。
2. B 打开房间页 → 提交申请；A 详情页出现「待处理申请 1」→ 批准。
3. B 详情页出现「进入房间」→ 点击 → 授权麦克风/摄像头 → 与 A **声画互通**（A 端能看到 B 的画面、听到声音）。
4. A 关摄像头、静音 → B 端看到头像块与静音徽标；反向再试一次。
5. A 在成员行把 B「设为协管」→ B 页面立刻出现「移出房间」按钮与待批申请区块。
6. 第三个浏览器 C（`mod@example.com`）申请 → B（协管）批准 → C 进房 → 现在 3/3 满员。
7. 第四个浏览器 D（新注册账号）申请 → 被拒并提示「房间已满（上限 3 人）」；A 侧同样无法批准（满员）。
8. A 把 B「移出房间」→ B 页面立刻出现「你已被移出房间」；B 刷新也回不来；A 侧成员列表该行标「被移出」。
9. B 再次提交申请 → A 批准 → B 重新进房（验证 FQ-3「立即允许」）。
10. A 在**底部控制坞右侧**点「结束房间」→ 坞内展开二次确认 → 确认 → 所有端立刻断开并显示「房间已结束」；房间转为只读，成员与历史消息仍可查（A 自己回到房间列表，卡片显示「已结束」）。
11. 回房间详情页确认：状态徽标「已结束」、成员退出原因（被移出 / 房间结束 / 主动离开）均可读。
12. （可选，验证 FQ-12）另开一间新房：两端进房后把其中一端的网络断掉 5~10 秒再恢复 → 徽标先「正在重连…」、随后自动回到「已连接」，声画恢复；期间库里不新增成员记录（`room_members` 行数不变）。
13. **等待页链路**：第四个账号 D 在列表页点「申请加入」→ 直接落等待页（呼吸光、三步时间线、房间卡与主题简介）→ A 在**交流页抽屉**里批准 → D 的等待页转「房主同意了，正在把你送进去」并在 1.5 秒后自动进入交流页；D 也可在获批前点「撤回申请」再「重新申请」。
14. **专注态**：交流页里鼠标静止 30 秒 → 状态条与控制条淡出；移动鼠标立即恢复；说话者格自动放大（其余格降权）。
